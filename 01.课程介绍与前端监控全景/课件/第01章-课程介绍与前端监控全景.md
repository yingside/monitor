## 1.1 从线上故障说起——前端监控能解决什么问题

### 白话先讲

想象这样一个场景：

> 你花了两周做了一个核心功能上线了。测试同学测了一遍，没问题。领导验收了一遍，没问题。但是上线后，有用户反馈说"这个按钮点了没反应"。你问用户用的什么手机、什么浏览器、点了什么，用户说"我也不知道，反正就是不好使"。

然后你就开始了大海捞针式的排查……

这就是**没有监控**的代价。前端监控要解决的，正是"你不在场时线上发生了什么"这个问题。

### 前端监控能具体解决哪些问题？

**1. 及时发现问题，而不是等用户投诉**

没有监控，你对线上的状态是盲的。有了监控，代码刚出错你就能收到告警，而不是等到第二天早上打开钉钉看到用户骂声一片。

**2. 快速定位问题，而不是凭直觉猜**

用户说"出错了"，你只能一行一行翻代码猜。有了监控，你能直接看到：
- 报错的完整堆栈信息（哪个文件第几行出错）
- 出错前用户做了什么（点了哪个按钮、跳了哪个路由）
- 出错时是什么设备、什么浏览器、什么操作系统

**3. 量化性能，而不是凭感觉说"慢"**

"这个页面好像有点慢"——这句话在技术会议上毫无意义。有了监控，你能说："这个页面的 LCP（最大内容绘制时间）在 P75 分位是 4.2s，超过了 Google 的 2.5s 良好标准，主要原因是首屏图片没有做懒加载。"这才是能推动优化的结论。

**4. 理解用户行为，而不是靠拍脑袋做产品决策**

用户到底在用哪些功能？哪个页面最容易被放弃？哪个按钮点击率最高？这些数据是产品决策的依据，而不是靠经验猜测。

### 小结

| 没有监控时 | 有了监控后 |
|-----------|-----------|
| 等用户投诉才知道出错 | 错误发生时立刻告警 |
| 凭直觉猜问题在哪 | 精确到文件、行号、上下文 |
| 感觉说"页面慢" | 数据说 P75 LCP = 4.2s |
| 拍脑袋做产品决策 | 用户行为数据支撑决策 |

## 1.2 前端监控的三大核心能力

一套完整的前端监控平台，本质上由三件事组成：

```
┌─────────────────────────────────────────────────────┐
│                                                     │
│   用户的浏览器                                       │
│   ┌──────────┐                                      │
│   │  你的网页 │  ← SDK 在这里悄悄运行，采集数据        │
│   └────┬─────┘                                      │
│        │ 数据上报                                    │
└────────┼────────────────────────────────────────────┘
         │
         ▼
┌─────────────────┐       ┌──────────────────┐
│  ① 数据采集与上报 │──────▶│  ② 数据整理与存储  │
│                 │       │                  │
│  SDK 在用户浏览器 │       │  后端接收数据、清洗 │
│  里运行，收集：   │       │  分类、存入数据库   │
│  - 错误信息      │       │                  │
│  - 性能指标      │       └────────┬─────────┘
│  - 用户行为      │                │
│  - API 状态      │                ▼
│                 │       ┌──────────────────┐
└─────────────────┘       │  ③ 数据展示与分析  │
                          │                  │
                          │  可视化平台，让你  │
                          │  看到图表、趋势、  │
                          │  告警、详情        │
                          └──────────────────┘
```

**① 数据采集与上报（SDK）**：跑在用户浏览器里的一段 JS 代码。它像一个"无声的观察者"，监听页面的错误、记录性能指标、追踪用户行为，然后把这些数据发送给后端。这就是我们常说的 **SDK（Software Development Kit，软件开发工具包）**。

**② 数据整理与存储（后端服务）**：SDK 上报的原始数据，需要被后端接收、校验、分类，然后存入适合查询和分析的数据库里。这一步解决"数据存在哪、怎么存"的问题。

**③ 数据展示与分析（可视化平台）**：把数据库里的数据变成人能看懂的图表、列表、详情页。这一步解决"数据怎么看、怎么用"的问题。

> **本课程会完整实现这三个部分**，这也是和只讲 SDK 的课程最大的不同。

> 🏗️ **架构思考：为什么要把这三件事拆开，而不是塞进一个服务里？**
>
> 这是软件工程中「关注点分离（Separation of Concerns）」原则的体现。分开的好处：
> - **SDK 只管采集**，不关心数据怎么存——将来换数据库，SDK 代码不用改
> - **存储层只管存**，不关心前端怎么展示——将来换展示方案，存储不受影响
> - **每一层都可以独立扩展、独立替换**
>
> **这种思维贯穿整个课程**：每做一个设计决策，都应该问自己——"这个模块的职责边界在哪里？"

## 1.3 主流监控平台横向对比

在自己动手做之前，先看看业界成熟的方案是什么样的。

### Sentry

**官网**：[sentry.io](https://sentry.io)

Sentry 是目前最流行的开源前端监控平台，功能覆盖错误监控、性能监控、Session Replay（录屏回放）、告警通知等。支持几乎所有主流前端框架（React、Vue、Angular、Next.js 等）。

**核心特点**：
- SDK 接入简单，几行代码即可接入
- 错误聚合能力强（相同错误会被合并为一条，而不是几千条重复记录）
- 开源（可自部署），也提供 SaaS 托管版本
- 我们课程的架构设计主要参考 Sentry

**适用场景**：面向开发者的错误与性能监控，开源项目、中小团队的首选。

---

### 阿里 ARMS（Application Real-Time Monitoring Service）

**官网**：[阿里云 ARMS](https://www.aliyun.com/product/arms)

阿里巴巴自研的应用性能监控平台，是阿里云的商业产品。除了前端监控，还覆盖后端 APM（应用性能管理）、链路追踪等。

**核心特点**：
- 与阿里云生态深度绑定（OSS、SLS 日志服务等）
- 支持小程序、Hybrid App 等特殊场景
- 商业产品，按量计费

**适用场景**：已经在用阿里云的团队，需要全栈（前端+后端）一体化监控的场景。

---

### 百度灯塔（F2）

百度自研的前端性能与数据统计平台，主要聚焦在页面性能指标采集和用户行为分析。在百度系产品中大量使用。

---

### 神策数据

**官网**：[sensorsdata.cn](https://www.sensorsdata.cn)

神策不是传统意义上的"前端报错监控"，而是**用户行为分析平台**。它的核心是埋点数据的采集、存储和分析，帮助产品和运营团队理解用户行为，做漏斗分析、留存分析等。

**适用场景**：产品、运营驱动的用户行为分析，与前端错误监控是互补关系，而非替代关系。

---

### 横向对比总结

| 维度 | Sentry | 阿里 ARMS | 灯塔 | 神策 |
|------|--------|----------|------|------|
| **定位** | 错误+性能监控 | 全栈 APM | 性能统计 | 用户行为分析 |
| **是否开源** | ✅ 开源可自部署 | ❌ 商业产品 | ❌ 内部 | 部分开源 |
| **接入成本** | 低（几行代码） | 中（需阿里云账号） | 中 | 中（需接入 SDK + 埋点） |
| **适合场景** | 开发者、中小团队 | 阿里云用户 | 百度系 | 产品/运营分析 |

> **本课程架构参考 Sentry**：因为 Sentry 开源、思路清晰、生态完善，是学习前端监控系统设计最好的参考对象。

## 1.4 Sentry 快速体验

> **目的**：在自己动手实现之前，先以用户身份感受一遍 Sentry 的完整体验——从接入 SDK 到看到第一条错误。这样后面设计自己的系统时，会更有方向感。

### 步骤一：注册并创建项目

1. 访问 [sentry.io](https://sentry.io)，点击 **Get Started** 免费注册
2. 登录后点击 **Create Project**
3. 选择平台：**React**（或者 **Vue**，根据你熟悉的框架选）
4. 给项目起名（如 `my-test-app`），点击 **Create Project**
5. Sentry 会给你展示一个 **DSN**，形如：
   ```
   https://xxxxxxxx@o123456.ingest.sentry.io/xxxxxxxx
   ```

   > 📖 **术语：DSN（Data Source Name，数据源名称）**
   >
   > 白话理解：就是你这个项目的「快递收件地址」。SDK 采集到数据后，就往这个地址发送。每个项目都有唯一的 DSN，后端通过 DSN 来区分数据属于哪个项目。
   >
   > DSN 的格式通常是：`https://公钥@服务器地址/项目ID`。公钥用于身份验证（证明这条数据确实来自你的项目），项目 ID 用于数据路由。我们后续也会自己实现一个类似的 DSN 机制。

### 步骤二：在项目中接入 SDK

新建一个 Vite + React 项目（或使用现有项目），安装 Sentry SDK：

```bash
npm install --save @sentry/react
```

在项目入口文件（`main.tsx`）中初始化：

```typescript
import * as Sentry from '@sentry/react'

Sentry.init({
  // 替换为你自己的 DSN
  dsn: 'https://你的DSN地址',
  // 性能采样率：1.0 表示采集 100% 的请求（开发时可以用 1.0，生产建议降低）
  tracesSampleRate: 1.0,
})
```

### 步骤三：手动触发一个错误

在任意组件中加一个按钮：

```typescript
function App() {
  return (
    <button
      onClick={() => {
        // 手动抛出一个错误，模拟线上 Bug
        throw new Error('这是一个测试错误，用于验证 Sentry 接入是否成功')
      }}
    >
      触发测试错误
    </button>
  )
}
```

点击按钮，错误被抛出。

### 步骤四：在 Sentry 控制台查看上报结果

回到 Sentry 控制台，等待几秒后刷新页面，你会看到：
- **Issues 列表**：出现了刚才抛出的那条错误
- **点击进入详情**，可以看到：
  - 错误消息和完整的调用堆栈（Stack Trace）
  - 发生时间、浏览器信息、操作系统
  - 影响的用户数量
  - 错误发生前的面包屑记录（Breadcrumbs，即用户的操作轨迹）

> 📖 **术语：Stack Trace（调用堆栈 / 错误堆栈）**：错误发生时，程序记录的「函数调用链」。白话就是：下面第一行出错，是被上面第二行调用的，而第二行又是被第三行调用的……都列出来。有了它，你就知道错误具体在哪个文件、第几行。
>
> 📖 **术语：Breadcrumbs（面包屑）**：借用《糖果屋》童话里小孩留下面包屑找路的典故。在监控领域指的是：错误发生前，用户的操作轨迹记录（例如点击了哪个按钮、跳了哪个路由、发了哪个请求）。有了它，你可以还原用户当时在干什么。

### 体验总结

通过这次快速体验，你应该感受到了：
- **接入成本极低**：两行代码（`install` + `init`）就能跑起来
- **数据自动采集**：不需要在每个 `try-catch` 里手动上报，SDK 自动帮你监听
- **数据很丰富**：一条错误背后有大量的上下文信息

这就是我们要实现的目标，接下来我们来拆解它的内部构造。

## 1.5 从 Sentry 反推：一套监控系统由哪些部分组成

刚才体验完 Sentry，现在我们"拆开看看"——实现这样一个系统，背后需要哪些东西？

### 拆解一：SDK 层（跑在用户浏览器里）

Sentry 的 `@sentry/react` 包安装到你的项目后，它在浏览器里做了这些事：

```
SDK 初始化（调用 Sentry.init()）
      │
      ├── 劫持 window.onerror 和 window.addEventListener('error')
      │   → 监听 JS 运行时错误
      │
      ├── 劫持 window.onunhandledrejection
      │   → 监听 Promise 未捕获异常
      │
      ├── 包装 React 错误边界（ErrorBoundary）
      │   → 监听 React 组件层错误
      │
      ├── 拦截 fetch 和 XMLHttpRequest
      │   → 监听 API 请求成功/失败/耗时
      │
      ├── 监听 PerformanceObserver
      │   → 采集 LCP、CLS、INP 等性能指标
      │
      └── 采集设备信息、路由变化、用户行为
          → 构建 Breadcrumbs（面包屑）
```

以上数据最终被打包成一个 JSON，通过 HTTP 请求发送到 DSN 对应的后端地址。

### 拆解二：数据接收后端（DSN 服务）

Sentry 后端接收到 SDK 上报的数据后：
1. **校验 DSN**：判断上报来源是否是合法的注册项目
2. **速率限制**：防止异常情况下的数据洪峰打垮服务
3. **数据入队**：把数据放入消息队列（类似 Kafka），避免直接写数据库产生的压力

### 拆解三：数据存储层

Sentry 使用多种数据库来存储不同类型的数据：
- **业务数据**（用户账号、项目信息）：PostgreSQL 等关系型数据库
- **监控事件数据**（大量日志）：**列式分析型数据库**（适合海量数据的聚合分析）

> 📖 **术语：OLAP 数据库（列式存储）**：OLAP 是「联机分析处理」的缩写。列式数据库不是把每一行数据放在一起，而是把每一列放在一起。这样做聚合查询（统计某列的求和、平均、按组分类）的速度极快。常见的列式分析库有 ClickHouse、Apache Doris 等，我们具体选哪个在后续章节确定。

### 拆解四：数据消费与处理

- 消息队列里的数据被消费服务读取
- 进行数据清洗、去重、聚合（相同错误合并为一条）
- 写入最终的存储层

### 拆解五：可视化平台（前端 Dashboard）

- 从数据库查询聚合后的数据
- 展示为图表（错误趋势、性能分布等）
- 提供搜索、筛选、告警配置等交互

### 完整链路图

```
用户浏览器
┌──────────────────────────┐
│    你的网页 + Sentry SDK   │
│                          │
│  收集错误/性能/行为数据    │
│         │                │
│     HTTP 上报             │
└─────────┼────────────────┘
          │
          ▼
┌──────────────────────────┐
│      DSN 接收服务          │
│  校验 → 限流 → 入消息队列  │
└─────────┼────────────────┘
          │
          ▼
┌──────────────────────────┐
│       消息队列（Kafka）    │
│  缓冲高峰流量、解耦生产消费 │
└─────────┼────────────────┘
          │
          ▼
┌──────────────────────────┐
│       消费者服务           │
│  数据清洗 → 聚合 → 写入 DB │
└─────────┼────────────────┘
          │
    ┌─────┴─────┐
    ▼           ▼
┌────────┐  ┌────────────┐
│业务数据库│  │ 监控数据库  │
│(PostgreSQL)│(列式分析 DB) │
└────────┘  └─────┬──────┘
                  │
                  ▼
    ┌─────────────────────────┐
    │      API 服务            │
    │  查询聚合数据，提供接口   │
    └──────────┬──────────────┘
               │
               ▼
    ┌─────────────────────────┐
    │    前端可视化平台         │
    │  图表 / 错误列表 / 详情   │
    └─────────────────────────┘
```

**这就是我们本课程要完整实现的系统。**

> 🏗️ **架构思考：分层的价值——每一层只做一件事**
>
> 上面这张链路图中，每个方框之间的边界切分得非常清晰。这种分层设计带来的好处很实际：
> - 上报高峰期 SDK 爆量？——Kafka 层吸收，不会冲垮后端
> - 想把数据库从 A 换成 B？——只需要改消费层，SDK 和前端展示层不用动
> - 想大规模扩容？——每一层都可以独立水平扩展
>
> **这就是为什么大型系统少不了分层架构的原因：不是为了复杂而复杂，而是为了处处可拆换、处处可扩展。**

## 1.6 本课程要做什么——完整架构图与各模块职责

### 我们要做的系统

```
monitor/（pnpm Monorepo 项目）
│
├── packages/                    ← SDK 层（你的监控代码核心）

│   ├── @monitor/browser         浏览器 SDK 入口：组合所有采集能力
│   ├── @monitor/browser-utils   工具函数：UUID生成、元素路径、设备信息等
│   ├── @monitor/vue             Vue3 插件适配层
│   └── @monitor/react           React 适配层
│
├── demos/                       ← 接入 SDK 的示例项目（演示 SDK 用法）
│   ├── vue3-demo/               Vue3 示例
│   └── react-demo/              React 示例
│
├── apps/backend/                ← 后端服务
│   ├── dsn-server/              数据接收服务：接收 SDK 上报 → 写入 Kafka
│   └── monitor-server/          平台 API 服务：用户/项目管理 + 列式分析库数据查询
│
├── apps/frontend/               ← 前端可视化平台
│   └── monitor/                 React + shadcn/ui 监控看板
│
└── docker/
    └── docker-compose.yml       ← 本地开发环境基础设施（Kafka + 列式分析库 + PostgreSQL）
```

### 各模块职责一览

| 模块 | 技术 | 职责 |
|------|------|------|
| `@monitor/core` | TypeScript | SDK 核心：初始化流程、插件注册机制、数据管道 |
| `@monitor/browser` | TypeScript | 浏览器 SDK 入口：错误/性能/行为/API 采集插件组合 |
| `@monitor/vue` | TypeScript + Vue3 | Vue3 框架层错误接入、Router 钩子集成 |
| `@monitor/react` | TypeScript + React | React ErrorBoundary、Router 集成 |
| `dsn-server` | NestJS | 接收 SDK 上报数据，写入 Kafka |
| `monitor-server` | NestJS + TypeORM | 用户/项目 CRUD，从列式分析库查询监控数据 |
| `monitor`（前端） | React + shadcn/ui | 可视化看板：错误/性能/行为/API 数据展示 |
| Docker Compose | Docker | 本地启动 Kafka + 列式分析库 + PostgreSQL |

## 1.7 课程约定：技术选型说明

### 为什么用 pnpm Monorepo？

SDK 有多个包（core、browser、vue、react），后端有两个服务，前端有一个平台，demos 有示例项目——它们之间需要互相引用、共享类型、统一构建。Monorepo（单仓库多包）能让这一切都在一个项目里管理，而不是分散在 N 个独立仓库里，开发体验更流畅。

pnpm 是目前最快且最节省磁盘空间的包管理器，特别适合 Monorepo 场景。

### 为什么监控数据需要列式分析库，而不用 MySQL？

监控数据的特点是：**写入量极大、查询方式是聚合分析**（统计某段时间内的错误数量、按页面分组的 PV 等）。

普通的关系型数据库（如 MySQL）按行存储，做聚合查询需要扫描大量不需要的字段，性能差。

**列式存储数据库**专门为聚合分析优化。简单说：普通数据库查"这张表的某列的平均值"需要把每一行都读出来，列式库只需要读那一列的数据，速度快 10 倍到 100 倍。

> **类比**：MySQL 像一本书，你要找某章里所有出现过"前端"这个词，得翻遍整本书每一页每一行。列式库像一个单词索引，按列直接定位，快得多。

目前主流的列式分析库有 **ClickHouse**、**Apache Doris** 等，它们都能胜任监控数据存储的场景，具体选哪个，我们在基础设施章节进行对比和确定。

> 🏗️ **架构思考：技术选型的思路——不是哪个"更好"，而是哪个"更适合这个场景"**
>
> 选择数据库的关键问题不是"哪个技术更新更潮"，而是：
> 1. **数据的读写模式是什么？**（监控数据是大量写入 + 聚合查询，不是频繁点查和事务）
> 2. **数据规模大概是多少？**（监控日志可能每天上亿条）
> 3. **团队运维能力如何？**（太复杂的方案维护成本高）
>
> **这种选型思维比"学会任意一种数据库的操作"更重要。**

### 为什么引入 Kafka？

SDK 上报是一个**高并发、高峰值**的场景——节假日活动时，可能同时有几万个用户在使用你监控的系统，错误数据洪峰可能在几秒内把后端打垮，直接写数据库来不及。

Kafka 是一个**消息队列**（更准确的说法是分布式事件流平台）。它就像一个"蓄水池"：

```
上报高峰来了 → 数据先进蓄水池（Kafka）→ 消费者按自己的速度慢慢从里面取
```

数据不会丢，服务不会崩，写入速度和处理速度解耦了。

### 为什么前端平台用 Vite + React + shadcn/ui + Tailwind？

- **Vite**：现代前端构建工具，开发体验远好于 Webpack
- **React**：当前最主流的前端框架，生态最完整
- **shadcn/ui**：不是传统的组件库（不需要 install 一个黑盒包），而是把组件源码直接复制到你项目里，完全可定制。配合 Tailwind CSS 使用，开发速度极快
- **Tailwind CSS**：原子化 CSS，不需要写 CSS 文件，直接在 className 里写样式，非常适合快速搭建 UI
- **Lucide**：轻量、统一的图标库，与 shadcn/ui 默认搭配

### 技术选型总览

| 层次 | 技术 |
|------|------|
| Monorepo 管理 | pnpm workspace + Turborepo |
| SDK | TypeScript，支持原生 JS / Vue3 / React |
| 数据上报 | fetch / Navigator.sendBeacon |
| 后端框架 | NestJS + TypeScript |
| 消息队列 | Apache Kafka |
| 监控数据库 | 列式 OLAP 库（ClickHouse / Apache Doris，具体选型见第 12 章） |
| 业务数据库 | PostgreSQL |
| 前端平台 | Vite + React + shadcn/ui + Tailwind CSS + Lucide + Recharts |
| 全局状态 | Zustand |
| 本地基础设施 | Docker Desktop + docker-compose |
