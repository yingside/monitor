## 2.1 监控系统功能需求梳理

### 先问自己：我们到底要采集什么？

上一章我们体验了 Sentry，感受到了监控系统能做什么。但现在要自己做一个，第一个问题就是：

> **"到底要采集哪些数据？"**

这个问题很关键。如果只是模糊地说"采集错误、采集性能"，后面写代码的时候会一直陷入"这个要不要采？那个要不要加？"的纠结。**需求梳理就是要在写第一行代码之前，把这些问题想清楚。**

我们把需求分成四大类：

---

### 一、错误监控

错误是最核心的监控能力。前端的错误大致分为以下几种：

**1. JS 运行时错误**

代码执行时抛出的同步错误，比如访问了 `undefined.xxx`、数组越界等。这类错误会触发浏览器的 `window.onerror` 事件，是最容易捕获的一类。

**2. 资源加载错误**

图片、CSS、JS 脚本等静态资源加载失败。这类错误不会冒泡到 `window.onerror`，需要监听 `window.addEventListener('error', handler, true)` 捕获阶段才能抓到。

> 🏗️ **架构思考：为什么资源错误用不同的方式监听？**
>
> `window.onerror` 只处理 JS 执行异常，资源加载失败是网络层的事件，两者是完全不同的错误来源。这说明同样是"错误监控"，底层需要不同的监听机制——这也是为什么 SDK 内部要做模块化设计，而不是一个大函数解决所有问题。

**3. Promise 未处理异常**

在异步代码中，如果一个 `Promise` 被 `reject` 了，但没有 `.catch()` 或 `try/await` 处理，就会触发 `window.addEventListener('unhandledrejection')` 事件。现代前端代码大量使用异步，这类错误非常常见。

**4. 框架层错误（React / Vue）**

React 的组件渲染过程中抛出的错误，需要通过 `ErrorBoundary` 捕获；Vue 3 通过 `app.config.errorHandler` 全局注册。原生的 `window.onerror` 抓不到这些框架内部的错误。

**需要采集的错误字段（每条错误上报时携带）：**

| 字段 | 说明 |
|------|------|
| `type` | 错误类型（js-error / resource-error / promise-error / framework-error） |
| `message` | 错误消息文本 |
| `stack` | 完整调用堆栈（Stack Trace） |
| `filename` | 出错的文件名/URL |
| `lineno` | 行号 |
| `colno` | 列号 |
| `timestamp` | 发生时间（Unix 毫秒） |
| `pageUrl` | 发生时所在的页面 URL |
| `userAgent` | 浏览器/设备信息 |
| `appId` | 所属项目的标识（通过 DSN 解析出来） |

---

### 二、性能监控

> **先问：什么是"性能好"？**

"性能好"不是感觉，而是数字。Google 提出了 **Core Web Vitals（核心网页指标）**，这是目前业界最主流的前端性能标准，直接影响 SEO 和用户体验评分。

| 指标 | 全称 | 含义 | 良好标准 |
|------|------|------|---------|
| **LCP** | Largest Contentful Paint | 最大内容绘制时间：页面上最大的可见内容（通常是首屏图片或大块文字）渲染完成的时间 | ≤ 2.5s |
| **INP** | Interaction to Next Paint | 交互响应时间：用户点击/输入后，页面响应的延迟 | ≤ 200ms |
| **CLS** | Cumulative Layout Shift | 累积布局偏移：页面内容有没有"跳动"（如图片撑开导致文字位移） | ≤ 0.1 |

> 📖 **术语：Core Web Vitals（核心网页指标）**：Google 在 2020 年提出的一套衡量页面用户体验的量化标准，官方工具（Lighthouse、PageSpeed Insights）都基于这套标准评分。LCP 代表"加载速度感知"，INP 代表"交互流畅度"，CLS 代表"视觉稳定性"。

除了 Core Web Vitals，我们还需要采集页面加载时序数据（来自浏览器的 `Navigation Timing API`）：

| 字段 | 含义 |
|------|------|
| `dns` | DNS 解析耗时 |
| `tcp` | TCP 建连耗时 |
| `ttfb` | Time to First Byte（首字节时间）：从发出请求到收到服务器第一个字节的时间，能反映服务器响应速度 |
| `domReady` | DOM 解析完成时间 |
| `load` | 页面完全加载时间（含所有资源） |
| `fp` | First Paint：第一次有像素出现在屏幕上的时间 |
| `fcp` | First Contentful Paint：第一次有文字或图片内容出现的时间 |

### 三、用户行为监控

> **学生常问：用户行为监控和错误监控有什么关系？**

有了错误信息，你知道"出了什么错"，但不知道"用户是怎么操作到这个错误的"。用户行为数据就是这个"上下文"——它回答的是：出错之前，用户在干什么？

我们需要采集：

| 类型 | 采集方式 | 采集什么 |
|------|----------|---------|
| **PV / UV** | 路由变化时触发 | 页面访问量 / 独立访客数 |
| **页面停留时长** | `visibilitychange` + 路由离开 | 用户在每个页面停了多久 |
| **路由跳转记录** | 监听 `history.pushState` / `popstate` | 用户的导航路径 |
| **点击埋点** | 特定元素绑定事件 / 全局代理 | 按钮、链接的点击行为 |

> 📖 **术语：PV / UV**
>
> - **PV（Page View，页面访问量）**：每次页面被加载/切换算一次 PV。同一个用户刷新 10 次 = 10 PV。
> - **UV（Unique Visitor，独立访客数）**：去重后的用户数量。同一个用户刷新 10 次 = 1 UV。
>
> 两者都重要：PV 反映流量，UV 反映受众规模。

---

### 四、API 请求监控

前端页面的大多数功能依赖接口请求。接口挂了，页面就白屏；接口慢了，用户体验差。所以我们要监控：

| 字段 | 含义 |
|------|------|
| `url` | 请求的接口地址 |
| `method` | 请求方法（GET/POST 等） |
| `status` | HTTP 状态码 |
| `duration` | 请求耗时（毫秒） |
| `success` | 是否成功（2xx 为成功） |
| `requestBody` | 请求体（可选，注意脱敏） |
| `responseBody` | 响应体摘要（可选，注意脱敏） |

采集方式：劫持（monkey-patch） `window.fetch` 和 `XMLHttpRequest`，在请求发出前记录时间，在响应回来时计算耗时和结果。

> 🏗️ **架构思考：为什么要监控 API，而不只靠后端自己的日志？**
>
> 后端日志是"服务端视角"：它知道自己收到了什么请求、处理了多久、返回了什么状态。但它看不到：
> - 请求从用户浏览器发出到服务器这段网络的耗时（有可能 DNS 解析就花了 2 秒）
> - 某类用户（特定地区、特定网络）的接口成功率是否异常低
> - 请求从发出到收到响应，用户端的感知时间是多少
>
> 前端 API 监控是"客户端视角"，两者互补，才能完整定位问题。

---

### 需求汇总一览

| 监控类型 | 采集来源 | 核心指标 |
|---------|---------|---------|
| 错误监控 | `onerror` / `unhandledrejection` / 框架钩子 | 错误率、错误分布、受影响用户数 |
| 性能监控 | `PerformanceObserver` / Navigation Timing API | LCP / INP / CLS / TTFB / 页面加载时间 |
| 用户行为 | 路由监听 / DOM 事件 | PV/UV、停留时长、行为路径 |
| API 监控 | Fetch / XHR 拦截 | 成功率、P95 耗时、错误接口分布 |

## 2.2 数据流转链路设计

### 从一条数据的"一生"说起

当用户浏览器里发生一个错误，这条错误数据要经历什么，才能最终出现在我们的监控看板上？

让我们跟着一条数据走一遍：

```
① 用户浏览器里发生错误
   window.onerror 被触发
   SDK 收集错误信息，打包成 JSON
         │
         │ HTTP POST（fetch 或 sendBeacon）
         ▼
② DSN 接收服务（dsn-server）
   - 解析 DSN，识别这是哪个项目的数据
   - 简单校验（必填字段、格式检查）
   - 限流检查（防止某个项目的数据把服务压垮）
   - 把数据投递到 Kafka Topic
         │
         │ Kafka Producer 写入
         ▼
③ Kafka（消息队列）
   Topic: monitor.error / monitor.performance / ...
   数据先缓冲在这里，等待被消费
         │
         │ Kafka Consumer 拉取
         ▼
④ 消费者（dsn-server 内的 Consumer 模块，或独立服务）
   - 数据清洗（去掉不合法字段）
   - 错误聚合（相同错误合并）
   - 批量写入列式分析数据库
         │
         ▼
⑤ 列式分析数据库（error_logs 表）
   数据落地，等待查询
         │
         │ SQL 查询
         ▼
⑥ 监控平台 API 服务（monitor-server）
   根据前端请求，聚合查询数据（如：统计过去24h的错误数）
         │
         │ HTTP Response（JSON）
         ▼
⑦ 前端可视化平台（monitor）
   图表展示：错误趋势折线图、TOP 错误列表...
```

> **这就是一条监控数据从"出生"到"展示"的完整生命周期。**

> 🏗️ **架构思考：为什么 DSN 服务不直接写数据库，而要多一个 Kafka？**
>
> 这是一个学生经常问的好问题。
>
> 想象一下：你监控的 App 正在搞促销活动，1000 个用户同时在用，某个接口突然挂了，1000 条错误在 1 秒内涌进来。如果 `dsn-server` 直接写数据库：
> - 数据库的写入 QPS 突然飙升，可能直接卡死
> - 数据库卡死 → `dsn-server` 响应超时 → SDK 重试 → 更多请求涌入 → 雪崩
>
> 有了 Kafka 之后：
> - `dsn-server` 只负责把数据"扔进"Kafka，这个操作极快（微秒级）
> - 消费者按照自己的节奏从 Kafka 里取数据写库，不会被上游压垮
> - 即使消费者临时挂掉，数据还在 Kafka 里，恢复后继续消费，**数据不丢**
>
> 这就是「**生产者-消费者解耦**」的核心价值：**上报速度和处理速度不需要匹配。**

> 📖 **术语：QPS（Queries Per Second）**：每秒请求数，衡量服务处理能力的常用指标。数据库写入 QPS 过高时，会出现锁竞争、连接池耗尽等问题，导致响应变慢甚至崩溃。

---

### 数据上报的两种方式

SDK 把数据发给 `dsn-server` 时，会用到两种技术：

**1. `fetch`（主力方式）**

```
fetch(dsnUrl, {
  method: 'POST',
  body: JSON.stringify(payload),
  headers: { 'Content-Type': 'application/json' }
})
```

优点：灵活，可以设置请求头、携带认证信息、获取响应。
缺点：如果用户关闭页面时还有数据没发完，`fetch` 会被浏览器取消。

**2. `Navigator.sendBeacon`（页面卸载时的备选）**

```
navigator.sendBeacon(dsnUrl, JSON.stringify(payload))
```

> 📖 **术语：sendBeacon**：浏览器提供的一个专门用于"最后一刻数据上报"的 API。它能在页面卸载（用户关闭/跳转）时，保证数据被发出去，即使页面已经销毁，浏览器也会在后台把这条请求发完。代价是：不能获取响应，不能设置请求头（只能用默认 Content-Type）。

SDK 的策略：**正常情况用 `fetch`，监听到 `visibilitychange` 或 `beforeunload` 时切换为 `sendBeacon`**，确保数据不丢。

## 2.3 业务后端设计

### 先问：为什么需要"业务后端"？

上面的链路图里，我们有 `dsn-server` 专门接收 SDK 上报的数据。那为什么还需要一个独立的 `monitor-server`（业务后端）？

因为监控系统除了采集数据，还需要有**用户体系和项目管理**：

- 我要登录才能看数据（用户认证）
- 我要创建"项目"，每个项目有独立的 DSN（项目管理）
- 我要从数据库查错误列表、性能趋势（数据查询 API）

这些"业务逻辑"和"数据接收"的职责差异很大，如果放在一个服务里会很混乱。

> 🏗️ **架构思考：为什么要把 dsn-server 和 monitor-server 拆成两个服务？**
>
> 先看两者的特点：
>
> | | dsn-server | monitor-server |
> |---|---|---|
> | 请求量 | 极高（每个用户的每个错误都会触发） | 中低（只有登录监控平台的开发者才用） |
> | 响应要求 | 越快越好，不需要返回复杂数据 | 可以慢一点，但返回数据结构复杂 |
> | 安全要求 | 公开接口（任何 SDK 都能访问） | 需要登录鉴权 |
> | 扩容策略 | 可能需要水平扩展多个实例 | 单实例够用 |
>
> 如果合并，高频无鉴权的上报流量会影响到需要鉴权的管理接口，扩容也会一起扩，浪费资源。拆开之后，各自独立部署，各自按需扩容。

### monitor-server 的核心功能

**① 用户认证**

- 注册（邮箱 + 密码）
- 登录（返回 JWT Token）
- 鉴权中间件（保护需要登录才能访问的接口）

> 📖 **术语：JWT（JSON Web Token）**：一种无状态的身份认证方案。用户登录成功后，服务器签发一个包含用户信息的 Token（本质是一段加密的字符串），后续请求在 Header 里携带这个 Token，服务器验证 Token 的签名和过期时间，不需要查数据库就能确认用户身份。

**② 项目管理**

每个团队/项目都有一个独立的"监控项目"，主要字段：

| 字段 | 说明 |
|------|------|
| `id` | 项目唯一 ID |
| `name` | 项目名称（如"官网前端"） |
| `app_id` | 应用标识，SDK 初始化时传入 |
| `dsn` | 该项目专属的上报地址（由系统生成） |
| `owner_id` | 创建者（关联 users 表） |

**③ 数据查询 API**

前端可视化平台所有的数据都来自这里：

| 接口 | 功能 |
|------|------|
| `GET /errors` | 查询错误列表（支持分页、按类型/时间过滤） |
| `GET /errors/:id` | 查询错误详情（含完整 Stack Trace） |
| `GET /performance/overview` | 性能概览（LCP/CLS/INP 的中位数/P75） |
| `GET /behavior/pv-uv` | PV/UV 趋势（按时间分组） |
| `GET /api-monitor/list` | API 请求列表（按成功率/耗时排序） |

> 🏗️ **架构思考：查询接口为什么不直接让前端访问 Doris/分析库？**
>
> 理论上可以，但有几个问题：
> 1. **安全**：直接暴露数据库连接信息，有 SQL 注入风险
> 2. **权限**：没有登录鉴权，任何人都能查任何项目的数据
> 3. **灵活性**：数据库的表结构和前端需要的 JSON 格式往往不一样，需要在后端做字段映射和聚合
>
> **中间加一层 API 服务，是所有生产级系统的标配，不是画蛇添足。**

## 2.4 前端平台功能规划

### 我们要做哪些页面？

前端可视化平台（`apps/frontend/monitor/`）需要满足监控系统的日常使用场景：

```
/login                  登录页
/register               注册页

/projects               项目列表（我管理的所有监控项目）
/projects/new           创建新项目
/projects/:id           进入某个项目的监控看板
    └── /errors         错误监控看板
    └── /performance    性能监控看板
    └── /behavior       用户行为看板
    └── /api            API 监控看板
    └── /settings       项目设置（查看 DSN、修改项目信息）
```

### 各看板的核心内容

**错误监控看板（/errors）**

- 错误总量趋势折线图（今天 vs 昨天）
- 错误类型分布饼图（JS 错误 / 资源错误 / Promise 错误 / 框架错误）
- TOP 错误列表：按发生次数排序，显示错误消息、首次/末次发生时间、影响用户数
- 点击某条错误进入详情：完整 Stack Trace + Breadcrumbs 面包屑轨迹

**性能监控看板（/performance）**

- LCP / INP / CLS 评分卡片（绿/橙/红三级）
- 页面加载时序瀑布图（DNS → TCP → TTFB → DOM → Load）
- LCP 趋势折线图（按天/周趋势）
- 按页面 URL 分组的性能排行

**用户行为看板（/behavior）**

- 今日 PV / UV 数值卡片
- PV/UV 折线趋势（过去 7 天 / 30 天）
- 热门页面排行（按 PV 排序）
- 用户留存：平均页面停留时长

**API 监控看板（/api）**

- 接口总成功率（大数字展示）
- 成功率趋势折线图
- 慢接口排行（按 P95 耗时排序）
- 失败接口排行（按错误次数排序）

## 2.5 数据库分工说明

### 为什么需要两个数据库？

> **学生最容易问的问题：直接用一个 PostgreSQL 不行吗？**

**完全可以跑起来——但在数据量上去之后会很痛苦。**

我们分析一下两类数据的特征：

| | 业务数据 | 监控数据 |
|---|---|---|
| **代表数据** | 用户账号、项目信息 | 错误日志、性能记录、行为事件 |
| **数据量** | 小（项目可能就几十个，用户几百个） | 巨大（每天可能几百万甚至上亿条） |
| **写入频率** | 低（用户注册、创建项目） | 极高（每个用户的每次错误/性能采集都写入） |
| **查询方式** | 点查为主（查某个用户、某个项目） | 聚合分析（统计某时间段内的错误数量、平均 LCP） |
| **关系复杂度** | 高（用户关联项目、项目关联权限） | 低（每条日志相对独立） |
| **适合的数据库类型** | 关系型（PostgreSQL） | 列式分析型（ClickHouse / Apache Doris） |

> 🏗️ **架构思考：一个业务能不能一直用一个数据库？**
>
> 早期完全可以。很多初创公司一开始就是一个 MySQL 搞定一切。**但当两类数据的特征差异越来越大时，同一个数据库就会出现"顾此失彼"的问题**：
> - 为了支撑监控数据的高频写入，需要减少索引 → 影响业务查询性能
> - 为了支撑业务数据的复杂关联查询，需要加索引 → 影响写入性能
>
> 分库不是"过度设计"，而是**在合适的时机，用合适的工具解决合适的问题**。这个时机的判断，就是架构师的核心价值之一。

### PostgreSQL 负责什么

PostgreSQL 存储所有"业务数据"，用 TypeORM 管理：

```
users 表
├── id
├── email（唯一）
├── password_hash（bcrypt 加密存储，绝不明文）
├── created_at
└── updated_at

projects 表
├── id
├── name
├── app_id（SDK 初始化时用的标识，UUID，全局唯一）
├── dsn（完整的上报 URL，系统生成）
├── owner_id → 关联 users.id
├── created_at
└── updated_at
```

> 📖 **术语：bcrypt**：一种专门用于密码存储的哈希算法。与普通 MD5/SHA 的区别是：bcrypt 内置"加盐"（salt）机制，且计算耗时可配置（cost factor），让暴力破解的成本极高。存密码必须用 bcrypt，不能用 MD5。

### 列式分析库负责什么

列式分析库存储所有"监控日志数据"，按数据类型分 4 张表：

```
error_logs         错误日志表
performance_logs   性能日志表
behavior_logs      用户行为日志表
api_logs           API 请求日志表
```

每张表的具体字段设计在**第 13 章**详细展开。

> **这里只需要记住结论：监控数据和业务数据的特征不同，所以用不同的数据库，各自发挥所长。**

## 2.6 DSN 设计

### 先问：DSN 到底解决什么问题？

第一章我们提到了 DSN 是"项目的收件地址"。现在我们要自己设计一个 DSN 机制，先想清楚它要解决的问题：

1. **来源识别**：SDK 上报了一条数据，`dsn-server` 怎么知道这条数据属于哪个项目？
2. **合法性验证**：怎么防止有人随便伪造上报请求？
3. **路由**：一个 `dsn-server` 实例可能服务多个项目，怎么把数据路由到正确的处理逻辑？

### DSN 的格式设计

参考 Sentry 的设计思路，我们的 DSN 格式为：

```
https://{public_key}@{host}/api/report/{app_id}
```

| 部分 | 说明 |
|------|------|
| `public_key` | 项目的公钥，用于身份验证，防止随意伪造（注意：这是公开信息，客户端 JS 代码里能看到，不要存敏感信息） |
| `host` | `dsn-server` 的服务地址 |
| `app_id` | 项目唯一标识（UUID），用于数据路由 |

**示例**：
```
https://abc123def456@monitor.yourcompany.com/api/report/proj-uuid-xxxx
```

### DSN 的工作流程

```
① 用户在监控平台创建项目
   → 系统自动生成 app_id（UUID）+ public_key（随机字符串）
   → 拼装成 DSN 字符串，存入 projects 表

② 开发者把 DSN 配置到 SDK 初始化参数里
   @monitor/browser 初始化时解析 DSN，提取 host 和 app_id

③ SDK 上报数据时，在 HTTP Header 里携带 public_key
   POST https://{host}/api/report/{app_id}
   Authorization: Bearer {public_key}
   Body: { type: 'error', ... }

④ dsn-server 收到请求后：
   - 从 URL 提取 app_id
   - 从 Header 提取 public_key
   - 查询 projects 表，验证 app_id + public_key 是否匹配
   - 匹配 → 数据合法，入 Kafka
   - 不匹配 → 返回 401，拒绝
```

> 🏗️ **架构思考：public_key 暴露在前端代码里，安全吗？**
>
> 这是很多人第一次看到 DSN 时会有的疑问。
>
> 答案是：**这是有意为之的设计，不是安全漏洞**。
>
> DSN 里的 `public_key` 本质上和你在网页里放 Google Analytics 的 Measurement ID 是一样的道理——它是一个"门牌号"，不是"密钥"。有人拿到你的 DSN 能干什么？
> - 向你的项目发送虚假监控数据（刷数据）
> - 但无法访问你的监控平台（那需要账号密码 + JWT）
> - 无法读取其他项目的数据
>
> 防刷数据的手段是**限流**（rate limiting）：每个 app_id 每分钟最多接受 N 条上报，超出丢弃。这就够了。
>
> **真正需要保密的是账号密码和 JWT，不是 DSN。**

## 本章小结

本章完成了整个系统的"图纸绘制"，后续所有代码实现都围绕这张图纸展开。

| 知识点 | 核心结论 |
|--------|---------|
| 功能需求 | 四大类：错误 / 性能 / 用户行为 / API 监控 |
| 数据链路 | SDK → DSN 服务 → Kafka → 消费写库 → API → 前端展示 |
| 为什么加 Kafka | 解耦生产消费，吸收上报高峰，保证数据不丢 |
| 两个后端服务 | dsn-server（高频无鉴权，接收上报）vs monitor-server（低频有鉴权，业务API） |
| 两个数据库 | PostgreSQL（业务数据，点查）vs 列式分析库（监控日志，聚合分析） |
| DSN 设计 | `public_key@host/app_id`，解决来源识别和合法性验证 |
| 前端平台 | 登录 + 项目管理 + 4个监控看板 |

> **关键原则回顾**：每一个"为什么这样分"的问题背后，都是「职责单一」+ 「按特征选工具」的架构思维。这两点是贯穿整个课程的核心设计哲学。
