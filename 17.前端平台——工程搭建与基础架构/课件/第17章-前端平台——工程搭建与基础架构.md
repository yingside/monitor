## 一、引言：前端平台的定位与目标

## 二、技术选型决策

> 🏗️ **架构思考**：为什么这些技术，而不是其他的？

### Vite + React + TypeScript

| 选择 | 原因 |
|---|---|
| Vite 6 | 最快的开发服务器（基于 esbuild），HMR 即时热更新，生产用 Rollup 打包 |
| React 18 | 生态最大，函数式组件 + Hooks 代码清晰，与第 7 章的 @monitor/react 适配包一致 |
| TypeScript | 全项目统一，配合后端 DTO 类型共享，减少运行时类型错误 |

**备选方案**：Vue 3 + Nuxt（也是好选择，但与 demos 的 Vue3 Demo 区分使得架构清晰）

### Tailwind CSS

> 📖 **Tailwind 是什么？**
>
> 白话：Tailwind 是"原子化 CSS 工具类"——把 CSS 属性拆成单独的类名，直接写在 JSX 里，不需要另写 CSS 文件。
>
> 术语：Utility-First CSS Framework

```jsx
// 传统写法
<div className="card-container">...</div>
// 还要另写 .card-container { display: flex; border-radius: 8px; ... }

// Tailwind 写法
<div className="flex rounded-lg border border-border bg-card p-4">...</div>
// 直接完成，不需要额外 CSS 文件
```

**核心优势**：
- 样式就在 JSX 旁边，一眼看清
- 不会有"僵尸 CSS"（Tailwind 按使用情况自动 purge）
- 约束设计系统（间距、颜色全部基于配置文件）

### shadcn/ui

> 📖 **shadcn/ui 是什么？**
>
> 白话：这不是一个你 `npm install` 进来的组件库——它是一套"把代码复制到你项目里"的方案。
>
> 术语：Copy-paste Component System（基于 Radix UI 原语 + Tailwind 样式）

**为什么选它？**
- 组件代码在你自己的 `src/components/ui/` 里，完全可以改
- 基于 `@radix-ui/react-*`，无障碍（accessibility）处理已做好
- 支持 `class-variance-authority`（cva），组件变体系统规范统一

**备选**：Ant Design / MUI —— 但这些是"黑盒"库，主题定制复杂，且默认是亮色主题，改成 Sentry 暗紫风格代价太大

### react-router-dom v6

> 📖 **createBrowserRouter 是什么？**
>
> 白话：React Router 6.4+ 的新路由器，把路由表定义为一个 JavaScript 对象数组，支持 Loader、Action 等数据加载功能。
>
> 比 v5 的 `<Route>` JSX 写法更清晰，路由表集中管理。

### Zustand

> 📖 **Zustand 是什么？**
>
> 白话：一个极简的全局状态管理工具——比 Redux 代码少 80%，功能够用。
>
> 核心 API：`create()`（创建 store）+ `persist()`（持久化到 localStorage）。

**备选**：Jotai、Redux Toolkit ——Jotai 更原子化，RTK 更企业级，但对这个规模的项目 Zustand 是最甜点

### Axios 封装

> 📖 **为什么不直接用 fetch？**
>
> `fetch` 没有拦截器机制，无法统一做：自动注入 JWT Token、401 自动退出登录、超时配置。封装 Axios 实例后，这些都自动处理，组件里只写业务逻辑。

### 3.2 Tailwind CSS 配置

**`tailwind.config.ts`** —— 配置了两套颜色系统：

**① shadcn/ui 语义色（CSS 变量驱动）**

在 tailwind.config.ts 中引用 CSS 变量：
```ts
colors: {
  background: 'hsl(var(--background))',
  foreground: 'hsl(var(--foreground))',
  primary: { DEFAULT: 'hsl(var(--primary))', ... },
  // ...
}
```

在 `src/index.css` 中定义变量（永久暗色，直接在 `:root`）：
```css
:root {
  --background: 258 40% 14%;   /* #1f1633 */
  --primary: 247 44% 57%;      /* #6a5fc1 */
  --accent: 77 83% 62%;        /* #c2ef4e */
  /* ... */
}
```

> 🏗️ **架构思考**：为什么用 HSL 变量，不直接用 hex？
>
> HSL 变量方案是 shadcn/ui 的约定：
> - `hsl(var(--primary))` 可以用 Tailwind 的不透明度修饰器：`bg-primary/50`（50% 透明度）
> - 在 CSS 中动态修改变量就能改主题，无需重新 build
>
> hex 方案不支持 `bg-[#6a5fc1]/50` 这种写法（Tailwind 无法自动分解 hex 的 RGB 通道来计算透明度）。

**② Sentry 品牌色（直接 hex）**
```ts
sentry: {
  bg: '#1f1633',
  lime: '#c2ef4e',
  purple: '#6a5fc1',
  // ...
}
```

用法：`bg-sentry-bg`、`text-sentry-lime`（需要精确颜色时使用）

### 3.3 PostCSS 配置

```js
// postcss.config.js
export default {
  plugins: { tailwindcss: {}, autoprefixer: {} }
}
```

Tailwind v3 通过 PostCSS 插件运行，Vite 会自动拾取 `postcss.config.js`。

### 3.4 shadcn/ui 配置

`components.json` 是 shadcn/ui CLI 的配置文件，告诉 CLI 组件放在哪里、别名是什么：

```json
{
  "style": "default",
  "tailwind": { "css": "src/index.css", ... },
  "aliases": { "components": "@/components", "utils": "@/lib/utils", ... }
}
```

> ⚠️ **课程深度说明**：本课程不使用 `npx shadcn@latest add button` 命令行自动添加，而是手动复制组件代码。原因：
> - CLI 依赖网络下载，课程环境可能受限
> - 手动复制让学生看到每个组件的完整代码
> - 可以直接按 Sentry 风格定制，不需要二次改造

## 五、工具层：cn 函数

```typescript
// src/lib/utils.ts
import { clsx, type ClassValue } from 'clsx'
import { twMerge } from 'tailwind-merge'

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(inputs))
}
```

> 📖 **cn 函数是什么？**
>
> 白话：一个"智能合并 class 名的函数"，专门解决 Tailwind 的冲突问题。
>
> 示例：
> ```tsx
> // 没有 cn：这样会有问题，两个 padding 会冲突
> <div className={`p-4 ${isLarge ? 'p-8' : ''}`} />
>
> // 用 cn：tailwind-merge 自动删掉被覆盖的 p-4，只保留 p-8
> <div className={cn('p-4', isLarge && 'p-8')} />
> ```

- `clsx`：处理条件类名（对象语法 / 数组 / 三元）
- `tailwind-merge`：解决 Tailwind 类名冲突（确保同类别的工具类只有最后一个生效）

## 六、工具层：Axios 封装

```typescript
// src/utils/request.ts
const request = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL ?? 'http://localhost:3003',
  timeout: 15000,
})

// 请求拦截器：自动注入 JWT
request.interceptors.request.use((config) => {
  const token = useAuthStore.getState().token
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截器：401 自动退出
request.interceptors.response.use(
  (res) => res,
  (error) => {
    if (error.response?.status === 401) {
      useAuthStore.getState().logout()
      window.location.replace('/login')
    }
    return Promise.reject(error)
  }
)
```

> 🏗️ **架构思考**：为什么在拦截器里用 `useAuthStore.getState()` 而不是 `useAuthStore()`？
>
> `useAuthStore()` 是 React Hook，只能在 React 组件内部调用。
> 拦截器是普通 JavaScript 函数，不在 React 组件树里，所以用 `.getState()` 直接读 store 的状态。
> 这是 Zustand 专门为非 React 场景设计的 API。

**环境变量**：在 `apps/frontend/monitor/` 根目录创建 `.env` 文件：
```
VITE_API_BASE_URL=http://localhost:3003
```

## 七、状态管理设计

### 7.1 auth.store.ts

```typescript
interface AuthState {
  token: string | null
  user: User | null
  setAuth: (token: string, user: User) => void
  setUser: (user: User) => void
  logout: () => void
  isAuthenticated: () => boolean
}
```

**持久化**：`persist` middleware 将 `token` 和 `user` 序列化到 localStorage（key: `monitor-auth`），页面刷新后自动恢复登录状态。

### 7.2 project.store.ts

```typescript
interface ProjectState {
  currentProject: Project | null       // 当前项目完整信息
  currentProjectId: string | null      // 当前项目 ID（持久化）
  setCurrentProject: (p: Project | null) => void
  setCurrentProjectId: (id: string | null) => void
  clearCurrentProject: () => void
}
```

> 🏗️ **架构思考**：为什么把 `currentProjectId` 和 `currentProject` 分开存？
>
> - `currentProjectId` 是持久化的——刷新后能恢复上次查看的项目
> - `currentProject` 不持久化——项目数据可能更新，每次进入时从 API 重新加载
> - 切换 ID 时清空 project 详情，强制页面重新加载最新数据

## 八、路由架构

### 8.1 路由结构设计

> 📖 **嵌套路由是什么？**
>
> 白话：子路由共享父路由的布局。例如所有监控页面都有 Sidebar + Header，这个公共布局就是父路由 `AppShell`，各个页面是子路由，渲染在 `<Outlet />` 位置。
>
> 不用嵌套路由的话，每个页面都要手写一遍 Sidebar + Header，代码重复。

```
Router（路由表）
├── / → 重定向 /projects
├── GuestGuard（已登录跳 /projects）
│   ├── /login → LoginPage
│   └── /register → RegisterPage
├── AuthGuard（未登录跳 /login）
│   └── AppShell（公共布局：Sidebar + Header）
│       ├── /projects → ProjectsPage
│       ├── /projects/:projectId → 重定向 errors
│       ├── /projects/:projectId/errors → ErrorsPage
│       ├── /projects/:projectId/performance → PerformancePage
│       ├── /projects/:projectId/behaviors → BehaviorsPage
│       └── /projects/:projectId/apis → ApisPage
└── * → NotFoundPage
```

### 8.2 AuthGuard 实现

```typescript
function AuthGuard() {
  const token = useAuthStore((s) => s.token)
  if (!token) return <Navigate to="/login" replace />
  return <Outlet />
}
```

> 📖 **为什么用路由层守卫，不在组件 useEffect 里 navigate？**
>
> - 路由层守卫在**渲染前**就决定走哪条分支，不会出现"先渲染了一半，再跳走"的闪烁问题
> - 更声明式：从路由表一眼看出哪些路由需要登录

### 9.2 Button variant 设计

```typescript
// class-variance-authority 变体定义
const buttonVariants = cva(
  // 基础样式（所有按钮共有）
  ['inline-flex items-center ...', 'uppercase tracking-[0.2px]', ...],
  {
    variants: {
      variant: {
        default: 'bg-primary text-primary-foreground shadow-inset-sm ...',
        secondary: 'bg-[#79628c] text-white border border-[#584674] shadow-inset-sm ...',
        // ...
      }
    }
  }
)
```

> 📖 **cva 是什么？**
>
> 白话：`class-variance-authority` 是一个"用对象配置来生成 class 字符串"的工具，让组件支持多种样式变体而不需要写复杂的 if-else。
>
> 对比没有 cva 的写法：
> ```tsx
> // 没有 cva：每次都要写 if-else 拼 className
> const cls = variant === 'primary' ? 'bg-primary ...' : variant === 'secondary' ? 'bg-secondary ...' : ...
>
> // 有 cva：声明式定义，调用时干净
> <Button variant="secondary" size="sm" />
> ```

## 十三、本章总结

> 🏗️ **架构思考**：前端工程基础层的核心价值

本章建立的不是具体功能，而是**整个前端的工程基础骨架**：

| 层次 | 组件/工具 | 作用 |
|---|---|---|
| **样式层** | Tailwind CSS + CSS 变量 | 统一的 Sentry 暗紫主题，全项目一致的设计语言 |
| **组件层** | shadcn/ui 基础组件 | 可复用的 UI 原语，后续章节直接使用 |
| **路由层** | react-router-dom v6 | 声明式路由 + 认证守卫，URL 即应用状态 |
| **状态层** | Zustand + persist | 全局认证状态持久化，跨页面共享数据 |
| **网络层** | Axios 封装 | 统一 JWT 注入 + 401 处理，组件无感知 |
| **类型层** | TypeScript 类型定义 | 与后端 DTO 对齐，编译时捕获接口变更 |

- 实现真实的项目 CRUD（创建 / 编辑 / 删除项目）
