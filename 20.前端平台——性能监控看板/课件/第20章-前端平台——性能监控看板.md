> 🏗️ **架构思考：为什么不新建接口，而是扩展现有接口？**
>
> - 前端查看一个时间段的性能数据，**4 个维度**（均值、趋势、分位、慢页面）同属一次"统计查询"
> - 合并成一个接口，**前端只发一次 HTTP 请求**，TanStack Query 缓存一份数据，4 个组件共享
> - 如果拆成 4 个接口，则并发 4 次请求，且缓存难以协同（时间范围一致但 key 分散）
> - 权衡：payload 略大 vs 请求次数少 + 缓存简单 → 选择扩展

## 20.1 Core Web Vitals 是什么

> 📖 **术语：Core Web Vitals（核心网页指标）**  
> 白话：Google 选出的"对用户体验影响最大的几个性能数字"，  
> 并把它们列为 SEO 排名因素之一。  
> 术语：由 Google 定义，用于衡量真实用户感知到的页面加载、交互和视觉稳定性的一组指标。

### 六大指标速查表

| 指标 | 全名 | 白话含义 | Good 阈值 | Poor 阈值 | 单位 |
|------|------|----------|-----------|-----------|------|
| **FCP** | First Contentful Paint | "页面上第一块内容出现"的时刻 | ≤ 1800ms | > 3000ms | ms |
| **LCP** | Largest Contentful Paint | "最大的那块内容完全渲染"的时刻，感知上的"加载完了" | ≤ 2500ms | > 4000ms | ms |
| **FID** | First Input Delay | 用户第一次点击到浏览器开始响应的延迟，衡量交互响应能力 | ≤ 100ms | > 300ms | ms |
| **CLS** | Cumulative Layout Shift | 页面元素乱跳的程度（广告插入、字体替换等导致）| ≤ 0.1 | > 0.25 | 无单位 |
| **TTFB** | Time to First Byte | 发出请求到收到服务器第一个字节，衡量服务器响应速度 | ≤ 800ms | > 1800ms | ms |
| **Load** | Load Time | 页面完整加载耗时（`loadEventEnd - navigationStart`） | ≤ 2500ms | > 5000ms | ms |

> ⚠️ **课程深度说明**  
> Google 2023 年宣布用 **INP（Interaction to Next Paint）** 替代 FID，作为新的"交互响应"指标。  
> 但我们的 SDK（第 8 章）采集的是 FID，ClickHouse 建表字段也是 `fid`，  
> 本章继续用 FID，了解 INP 的读者可以自行查阅 [web.dev/inp](https://web.dev/inp/)。

## 20.2 执行步骤

### Step 1：扩展后端 `getPerformanceStats`

> 📖 **术语：分位数（Quantile / Percentile）**  
> 白话：把所有用户的指标值从小到大排，P75 就是第 75% 位置的那个值。  
> 意思是：75% 的用户比这个快，只有 25% 的用户比这个慢。  
> 术语：统计学中表示一组数据累计频率分布的分割点。

**为什么需要分位数，不够均值吗？**

假设有 100 个用户 LCP 数据，99 个是 2000ms，1 个是 100000ms（网络超时）：
- 均值 = (99 × 2000 + 100000) / 100 = **2970ms** → 已超过 Good 阈值，很"差"
- P75 = 2000ms → **实际上 75% 用户体验很好**

均值被极端值拉偏，P75 更能反映"大多数用户"的真实感受。  
**Google 官方推荐以 P75 作为指标达标的评估基准。**

打开文件：  
`apps/backend/monitor-server/src/monitor-data/monitor-data.service.ts`

在 `getPerformanceStats` 方法中，将原来的 2 个并行查询扩展为 4 个：

```typescript
// 原来
const [avgRows, trendRows] = await Promise.all([...])

// 扩展后
const [avgRows, trendRows, quantileRows, topSlowPagesRows] = await Promise.all([
  // ① 原有：各指标均值
  this.clickhouse.query<Record<string, string>>(`SELECT round(avgIf(...`),

  // ② 原有：LCP 每日趋势
  this.clickhouse.query<{ date: string; avgLcp: string }>(`SELECT toDate(...`),

  // ③ 新增：关键指标 P50 / P75 / P95
  // quantileIf(level)(expr, cond) — 只统计满足 cond 的行，等价于先过滤后求分位数
  this.clickhouse.query<Record<string, string>>(`
    SELECT
      round(quantileIf(0.5)(fcp,  fcp > 0), 2)  AS fcp_p50,
      round(quantileIf(0.75)(fcp, fcp > 0), 2)  AS fcp_p75,
      round(quantileIf(0.95)(fcp, fcp > 0), 2)  AS fcp_p95,
      -- lcp、ttfb、load_time 同理...
    FROM performance_logs WHERE ...
  `),

  // ④ 新增：最慢页面 Top 10（按 avgLcp 降序）
  this.clickhouse.query<{...}>(`
    SELECT page, round(avgIf(lcp, lcp > 0), 2) AS avgLcp, ...
    FROM performance_logs WHERE ...
    GROUP BY page HAVING avgLcp > 0
    ORDER BY avgLcp DESC LIMIT 10
  `),
])
```

完整代码见 `monitor-data.service.ts`，return 结构扩展为：
```typescript
return {
  summary: { avgFcp, avgLcp, avgFid, avgCls, avgTtfb, avgLoadTime },
  lcpTrend: [...],
  quantiles: {
    fcp:      { p50, p75, p95 },
    lcp:      { p50, p75, p95 },
    ttfb:     { p50, p75, p95 },
    loadTime: { p50, p75, p95 },
  },
  topSlowPages: [{ page, avgLcp, avgFcp, count }],
}
```

> 🏗️ **架构思考：ClickHouse 的 `quantileIf` 与 `avgIf`**
>
> ClickHouse 有一类"条件聚合函数"，命名规律是 `函数名 + If(expr, condition)`：
> - `avgIf(fcp, fcp > 0)` — 只对 `fcp > 0` 的行求平均，排除未采集的 0 值
> - `quantileIf(0.75)(fcp, fcp > 0)` — 只对 `fcp > 0` 的行求 P75
>
> 这种做法比先 `WHERE fcp > 0` 再聚合的优势：  
> **可以在同一个查询里同时统计多个字段**，而不用为每个字段写单独的子查询。

### Step 3：服务层 `services/performance.service.ts`

新建 `apps/frontend/monitor/src/services/performance.service.ts`：

```typescript
import request from '@/utils/request'
import type { ApiResponse } from '@/types/api'
import type { PerformanceStats, PerformanceStatsParams } from '@/types/performance'

// GET /monitor/performance/stats
export async function getPerformanceStatsApi(
  params: PerformanceStatsParams,
): Promise<PerformanceStats> {
  const { data } = await request.get<ApiResponse<PerformanceStats>>(
    '/monitor/performance/stats',
    { params },
  )
  return data.data
}
```

> 🏗️ **架构思考：服务层的职责边界**
>
> 服务层只做两件事：
> 1. 拼请求参数、调 axios
> 2. 解包 `response.data.data`（去掉 `{ code, data, message }` 外层）
>
> **不做**：数据转换、错误处理、UI 逻辑——这些在 Hook 层和组件层处理。  
> 这样的好处是：如果后端 URL 变了，只改服务层这一个地方，Hook 和组件不用动。

### Step 4：Hook 层 `hooks/usePerformance.ts`

新建 `apps/frontend/monitor/src/hooks/usePerformance.ts`：

```typescript
import { useQuery } from '@tanstack/react-query'
import { getPerformanceStatsApi } from '@/services/performance.service'
import type { PerformanceStatsParams } from '@/types/performance'

export function usePerformanceStats(params: PerformanceStatsParams) {
  return useQuery({
    queryKey: ['monitor', 'performance', 'stats', params],
    queryFn: () => getPerformanceStatsApi(params),
    enabled: Boolean(params.appId),    // appId 为空时不发请求
    staleTime: 1000 * 60,              // 60 秒缓存
  })
}
```

>
> 在 `PerformancePage` 中，`startTime`/`endTime` 必须用 `useMemo` 计算，  
> 否则每次渲染都 `new Date()` 生成新字符串 → queryKey 每次不同 → 无限 isLoading。

> ```tsx
> // ✅ 正确：useMemo 保证 key 稳定
> const { startTime, endTime } = useMemo(() => getTimeRangeParams(timeRange), [timeRange])
>
> // ❌ 错误：每次渲染都生成新的时间字符串

### Step 5：VitalsCards 组件

新建 `apps/frontend/monitor/src/components/performance/VitalsCards.tsx`。

**核心逻辑：评级判断**

```typescript
function getRating(value: number, threshold: VitalThreshold): VitalRating {
  if (value === 0) return 'good'           // 0 = 无数据，不标"差"
  if (value <= threshold.good) return 'good'
  if (value <= threshold.poor) return 'needs-improvement'
  return 'poor'
}
```

**三段式进度条原理**

每张卡片底部有一个色彩渐变的进度条，直观展示当前值在评级区间中的位置：

```
|←──── Good ────→|←── Needs Impr. ──→|←── Poor ──→|
0ms           1800ms               3000ms        3600ms(max)
```

`fill = Math.min((value / (poor × 1.2)) × 100, 100)` — 以 Poor 阈值 1.2 倍为满值，  
超过满值时进度条拉满（不溢出）。

**完整阈值配置**（6 个指标）：

```typescript
const VITAL_THRESHOLDS = {
  FCP:  { good: 1800, poor: 3000, unit: 'ms' },
  LCP:  { good: 2500, poor: 4000, unit: 'ms' },
  FID:  { good: 100,  poor: 300,  unit: 'ms' },
  CLS:  { good: 0.1,  poor: 0.25, unit: '' },   // 无单位
```

### Step 6：LcpTrendChart 组件

**关键点：评级参考线（ReferenceLine）**

Recharts `ReferenceLine` 组件可以在图表上绘制水平参考线，用来标注 Good / Poor 的阈值：

```tsx
import { ReferenceLine } from 'recharts'

// Good 上限：2500ms
<ReferenceLine
  y={2500}
  stroke="#4ade80"
  strokeDasharray="4 3"
  strokeOpacity={0.5}
  label={{ value: 'Good', fill: '#4ade80', fontSize: 10, position: 'insideTopRight' }}
/>

// Poor 下限：4000ms
<ReferenceLine
  y={4000}
  stroke="#f87171"
  strokeDasharray="4 3"
  label={{ value: 'Poor', fill: '#f87171', fontSize: 10, position: 'insideTopRight' }}
/>
```

> 📖 **术语：ReferenceLine（参考线）**  
> 白话：图表上的一条横线，用来标注某个特定数值的位置（比如"及格线"）。  
> 通常用虚线绘制，颜色与主数据线不同，帮助用户对比当前值和阈值的关系。

## 20.3 完整数据流

```
URL: /projects/:projectId/performance

① useProjectStore.currentProject（Zustand, localStorage）
     ↓ 命中 → 直接取 project.appId
     ↓ 未命中（刷新/直链）→ useProject(projectId) → GET /projects/:id

② useMemo(() => getTimeRangeParams(timeRange), [timeRange])
     → { startTime, endTime }（key 稳定，避免无限 isLoading）

③ usePerformanceStats({ appId, startTime, endTime })
     → TanStack Query（enabled: Boolean(appId)）
     → GET /monitor/performance/stats?appId=...&startTime=...&endTime=...
     → ClickHouse 4 个并行查询（avgIf + 趋势 + quantileIf + 慢页面）
     → { summary, lcpTrend, quantiles, topSlowPages }

④ 分发给 4 个组件渲染
     summary      → VitalsCards（评分 + 进度条）
     lcpTrend     → LcpTrendChart（折线 + 阈值参考线）
     quantiles    → MetricsQuantileChart（分组柱状图）
     topSlowPages → SlowPagesTable（排名 + LCP 评级 badge）
```

## 20.4 本章涉及的 Recharts API 要点

| API | 用途 | 本章使用场景 |
|-----|------|-------------|
| `<LineChart>` | 折线图容器 | LCP 趋势图 |
| `<BarChart>` | 柱状图容器 | 分位数图 |
| `<Bar>` | 单个系列柱子（P50/P75/P95 各一个） | 分位数图 |
| `<ReferenceLine>` | 参考基准线 | LCP 趋势图（Good/Poor 阈值） |
| `<Legend>` | 图例（自动根据 Bar.name 生成） | 分位数图 |
| `<Tooltip content={<CustomTooltip />}>` | 自定义悬停提示 | 两个图表 |
| `<ResponsiveContainer>` | 宽度 100% 自适应容器 | 两个图表 |

> ⚠️ **课程深度说明**  
> Recharts 的 API 非常丰富（动画、自定义形状、复合图等），本课程只讲本章用到的部分。  
> 如需深入，参考 [recharts.org](https://recharts.org/en-US/)。
